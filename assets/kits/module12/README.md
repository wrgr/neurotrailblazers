# Module 12 kit: a query to profile

> **Synthetic teaching data.** Every number in this kit was generated by
> `scripts/generate_kit_materials.rb` from a fixed random seed. None of it is sampled from MICrONS, H01,
> FlyWire or any other real dataset, and no result computed from it is a finding
> about a brain. The distributions were chosen by hand so that one teaching point
> is visible; real data are messier in ways this kit does not model.

The query to profile in the Module 12 run-of-show (20:00-34:00) and the sampled
measurement in studio task 2. `profile_join.py` builds synthetic tables with the
shape of the studio scenario (a synapse table scaled from 5 x 10^8 rows, a
120,000-row segment table, cell types for 8,400 neurons) at a fraction you choose,
then times one question two ways:

1. **Join at query time:** for every synapse, look up the pre- and postsynaptic
   segment's neuron and that neuron's cell type, then count cell-type pairs.
2. **Pre-joined:** the same count from a table where the cell types were written
   onto each synapse row once, in advance.

```bash
python3 profile_join.py --fraction 0.001    # 0.1 % sample: 500,000 synapse rows
python3 profile_join.py --fraction 0.0005   # halve it and check the scaling is linear
```

It prints wall times, the extrapolation to the full table, and the ratio, as
JSON. Python 3, no packages, no network.

**What the numbers mean.** This is in-memory Python on your laptop. It shows the
method: measure a sample, check that time scales with rows, extrapolate, then
compare against a design that moves work out of the query. It does not estimate
what a query against cloud object storage costs, where reading bytes, not joining
them, usually dominates. Say that in your write-up.
